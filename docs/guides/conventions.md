# Code conventions

These are the rules for code in Coney: the C++ engine under `src/`, the asset tools under `tools/` and the Python
package under `python/`. They exist so that anyone can open a file, understand what it does and why, and find the
part of the original game it replaces. Reviewers check code against this page.

Coney is written from the research in `docs/research/`, never from decompiler output (see
[the clean room](research-workflow.md#clean-room) and
[LEGAL.md](repo:LEGAL.md#clean-room)). Several rules below, `@orig` tags and
research links above all, are there to keep the path from a line of our code back to its research visible.

The engine is still small. `coney::io::Reader` (`src/fileio/reader.h`) and the error codes below exist as shown;
the `WadIndex` example is a simplified version of `src/fileio/wad_index.h`, and `CONEY_ASSERT` takes only the
condition. Where the code differs from an example, the code is right and this page is updated to match it.

## Licence header

Every file of code we write starts with an SPDX line naming its licence, so the licence survives when a file is
copied out of the repository on its own:

```cpp
// SPDX-License-Identifier: GPL-3.0-or-later
```

```python
# SPDX-License-Identifier: GPL-3.0-or-later
```

The scope, precisely:

| Files | Header |
| --- | --- |
| Coney's own code: C++ sources and headers, Python, CMake files, shell and PowerShell scripts (such as `tools/start-ghidra-mcp.ps1`) | The SPDX line above, as the first line (after a `#!` line if the file has one). In a PowerShell script, leave a blank line after it: a comment directly above the `<# ... #>` help block hides that block from `Get-Help` |
| Code a generator writes into `src/`, `tools/` or `python/` | The same line; the generator emits it |
| Documentation in `docs/` | None. The whole folder is CC-BY-SA-4.0 through `docs/LICENSE`; a header would only clutter the rendered page |
| Generated documents (`docs/research/tables/`) | None. They carry a "generated by ..., do not edit" line instead and take the licence of the folder they live in |
| Files that cannot hold a comment (JSON such as `CMakePresets.json`) and small config files | None. They are covered by `LICENSE` at the repository root |

The licences themselves are set in [LEGAL.md](repo:LEGAL.md#licences): code
GPL-3.0-or-later, documentation CC-BY-SA-4.0.

## C++ {#cpp}

### Standard and compilers

Coney is written in **C++23**, limited to what all four supported compilers implement:

| Compiler | Minimum | Platform |
| --- | --- | --- |
| MSVC | 19.38 (Visual Studio 2022 17.8) | Windows |
| GCC | 13 | Linux |
| Clang | 17 | Linux |
| Apple Clang | Xcode 16 | macOS |

In practice that gives us `std::expected`, `std::span` and `std::format`, which the rules below rely on. We do not
use C++ modules: compiler and CMake support for them is still uneven across these four, and one platform failing to
build is worse than the benefit.

Every build is warning-free, and CI treats warnings as errors (`/W4 /WX` on MSVC; `-Wall -Wextra -Wpedantic
-Werror` elsewhere). A warning on one compiler is often a real portability bug on another.

### Build

CMake 3.28 or newer, driven by presets, with Ninja as the generator. Dependencies (SDL3, librw, Catch2) come in
through `FetchContent` and are pinned to exact versions in `cmake/deps.cmake`, so every machine builds the same
thing. Configure, build and test with one preset: `cmake --preset dev && cmake --build --preset dev && ctest
--preset dev` (on Windows, from a shell with the MSVC environment loaded by `vcvars64.bat`). The presets are `dev`,
`release`, `ci` (warnings as errors) and `asan` (AddressSanitizer and UBSan, Linux and macOS only).
Prerequisites, each preset and what CI runs are in [Building and testing](building.md).

### Formatting

clang-format does the formatting; nobody formats by hand. The configuration (`.clang-format` at the repository
root) is:

- the LLVM style as the base;
- 4-space indentation;
- lines of at most 120 columns.

pre-commit runs clang-format on every commit, so formatting never appears in review. Don't fight it with manual
alignment; if clang-format makes something unreadable, restructure the code instead.

### File layout

- **One class per header and source pair.** `wad_index.h` declares `WadIndex`, and `wad_index.cpp` defines it. A
  small helper type used only by that class may share its files.
- **Folders mirror the original source tree.** The original game was built from files under
  `c:/Warriors/Source/<Subsystem>/`; their paths survive in the executable's debug strings. Our code goes in
  `src/<subsystem>/`, with the folder and file names lowercased to `snake_case`:
  `c:/Warriors/Source/Human/Human.cpp` becomes `src/human/human.cpp`. Anyone holding an address, a research page or
  an original file name can then find our code, and the other way round. The PS2 device layer has no folder of its
  own: what it did is either part of a subsystem (the WAD index from `Device/ps2/fileio/` lives in `src/fileio/`)
  or platform code (`src/platform/`, see [Platform code](#platform-code)).
- **Folders appear with their first code.** Never create an empty placeholder folder.
- **Tests mirror `src/`.** The tests for `src/fileio/wad_index.cpp` go in `tests/fileio/wad_index_test.cpp`.
- Headers use `.h` and `#pragma once`, which all four compilers support and which can't go stale the way include
  guards can.

### Include order

Includes come in four groups, separated by a blank line, each sorted alphabetically:

1. the file's own header (in a `.cpp`), so a header that doesn't include what it needs fails to compile at once;
2. the C++ standard library (`<cstdint>`, `<expected>`, ...);
3. third-party libraries (SDL3, librw, Catch2);
4. other Coney headers, by path from `src/` (`"core/error.h"`, `"fileio/reader.h"`).

```cpp
// SPDX-License-Identifier: GPL-3.0-or-later
#include "fileio/wad_index.h"

#include <cstdint>
#include <span>

#include "core/error.h"
#include "fileio/reader.h"
```

Include what you use, and nothing else; never rely on a header arriving through another one.

## Naming

| What | Style | Example |
| --- | --- | --- |
| Files and folders | `snake_case` | `src/fileio/wad_index.cpp` |
| Namespaces | `lower` | `coney`, `coney::io` |
| Types (classes, structs, enums, aliases) | `PascalCase` | `WadIndex`, `WadDirEntry`, `ErrorCode` |
| Enumerators (always in an `enum class`) | `PascalCase` | `ErrorCode::Truncated` |
| Functions | `camelCase` | `parse`, `readU32Le` |
| Variables and parameters | `camelCase` | `entryCount`, `dirData` |
| Data members | `m_camelCase` | `m_entries` |
| Constants (`constexpr` and `const` at namespace or class scope) | `kPascalCase` | `kSectorSize` |
| Macros | `CONEY_UPPER` | `CONEY_ASSERT` |

All engine code is inside the `coney` namespace, with one nested namespace per subsystem (`coney::io` for disc and
file access). Macros carry the `CONEY_` prefix because they ignore namespaces and would otherwise collide with SDL3,
librw or the platform headers.

Names describe what the thing is in **our** design. They may match the original's name when that is the clearest
choice, but they don't have to: the clean room asks for our own names and structure, and the `@orig` tag (below)
records the original name, so nothing is lost. For example, the original `DVDWadIndex` becomes `WadIndex`, since
nothing in Coney reads from a DVD drive directly.

## Comments and @orig {#comments-and-orig}

Coney's comments are written for someone who will hand-write their own version of the subsystem from our code and
docs alone, and for a reviewer reading a diff without the docs open. That sets these rules.

1. **Every public type and function has a doc comment** (`///`), saying what it is for, what it returns and how it
   fails. A reader should be able to use it without opening the `.cpp`.
2. **Every other function has a comment above it too**: private members, helpers in an anonymous namespace, static
   functions, and lambdas longer than a few lines. One line saying what it does and why it exists is usually enough
   (`// Reads one chunk and runs its handlers: the loop body both loaders share.`). Skip it only where the name
   says everything (a getter, a one-line forwarder). A definition in a `.cpp` whose declaration already carries the
   doc comment needs none; don't repeat it.
3. **A long function is signposted**: a short comment before each step of a function that does several things, so a
   reviewer can follow it without holding the whole of it in their head.
4. **Tests say what they prove**: the `TEST_CASE` name states the behaviour, and a fixture or a hand-built byte
   layout gets a comment saying what it stands for.
5. **Short by default.** Most comments are one or two lines. Write longer only where the subject needs it: an
   invariant, a format quirk, a deliberate difference from the original. Never narrate the code line by line.
6. **Every non-obvious line explains why**, not what. `// Seek to 0x10` repeats the code; `// The 12 bytes after the
   count are padding: the entries start at 0x10` tells the reader something the code can't.
7. **The doc comment links the research page** that describes the behaviour, by its path in the repository
   (`docs/research/formats/wad-dir.md`), which works both in an editor and on GitHub.
8. **No commented-out code.** Git keeps the history; dead code in comments only makes the reader wonder whether it
   matters.

### The @orig tag

Everything that reimplements a function of the original game carries an `@orig` tag in its doc comment:

```text
@orig 0x<address> <OriginalName> (<File>.cpp)
```

- **Address:** the original function's entry point in the NTSC-U executable `SLUS_212.15`, written with eight hex
  digits (`0x001490b8`).
- **OriginalName:** the name the research database gives it (`research/symbols/*.yaml`, see
  [the research database](research-workflow.md#the-research-database)).
- **File:** the original translation unit's file name, when it is known. When it isn't, write `(unknown)` and fix
  the tag when research finds it.

One tag per original function. A Coney function that does the work of two original functions carries two tags; a
function with no original counterpart (our own glue, a helper the original inlined) carries none.

**Every tag is counted.** In the same commit as the code, add a `[[function]]` block for each newly tagged original
function to `docs/progress/functions.toml` (address, original name, subsystem and, when known, size), then run
`uv run --project python coney-tools progress update` and commit the regenerated tables. CI fails when a tag and the
file disagree. `coney-tools progress sizes --fill` finds a size from your own disc. Details:
[the progress commands](coney-tools.md#progress) and [Progress](../progress/index.md). Rekit's
`rekit research check` matches the tags against the research database in both directions, so a tag with a wrong
address, or a reimplemented symbol with no tag, is caught by CI once that check is in place.

### A complete example

The header below shows the doc comments, the research link and the `@orig` tags together. It is written from
[the WARRIORS.DIR research page](../research/formats/wad-dir.md), which describes the file layout and the lookup;
it is an illustration of the intended API, not code that exists yet.

```cpp
// SPDX-License-Identifier: GPL-3.0-or-later
#pragma once

#include <cstddef>
#include <cstdint>
#include <expected>
#include <span>
#include <string_view>
#include <vector>

#include "core/error.h"

namespace coney::io {

/// One entry of WARRIORS.DIR: where one file lives inside WARRIORS.WAD.
/// Layout: docs/research/formats/wad-dir.md
struct WadDirEntry {
    std::uint32_t wadOffset = 0; ///< Byte offset into WARRIORS.WAD; a multiple of 2048.
    std::uint32_t size = 0;      ///< Size of the file in bytes.
    std::uint32_t nameHash = 0;  ///< CRC-32 of the lowercased path (docs/research/name-hash.md).
};

/// The table of every file in WARRIORS.WAD, read from WARRIORS.DIR.
///
/// Research: docs/research/formats/wad-dir.md
class WadIndex {
public:
    /// Parses a complete WARRIORS.DIR image.
    /// Fails with ErrorCode::Truncated when the data is shorter than its entry count says.
    /// The original does this work in its constructor; a factory function can report failure, a constructor can't.
    /// @orig 0x00149160 DVDWadIndex::DVDWadIndex (DVDWadIndexPS2.cpp)
    static std::expected<WadIndex, Error> parse(std::span<const std::byte> dirData);

    /// Finds the entry for a path such as "./ee_files/global.lua", in any letter case.
    /// Returns nullptr when no entry matches. The pointer stays valid as long as this index.
    /// @orig 0x001490b8 DVDWadIndex::Find (DVDWadIndexPS2.cpp)
    const WadDirEntry* find(std::string_view path) const;

private:
    std::vector<WadDirEntry> m_entries;
};

} // namespace coney::io
```

## Errors

**The engine does not throw exceptions.** Exceptions make every call a possible exit that the code doesn't show,
which is hard to follow for someone reading a function for the first time, and they are costly to reason about at
the boundary with C libraries such as SDL3 and librw. Instead:

- **Recoverable errors** (a missing file, truncated data, a device that went away) return
  `std::expected<T, coney::Error>`. The caller sees in the signature that the call can fail and must decide what to
  do.
- **Programmer errors** (a broken invariant, an index out of range, a call in the wrong state) use `CONEY_ASSERT`.
  These are bugs, not situations to recover from, so the program stops and reports where.

The API, from `src/core/error.h` and `src/core/assert.h` (abridged: the enum has two more codes, and
`CONEY_ASSERT` takes only the condition):

```cpp
namespace coney {

/// What went wrong, in a form code can branch on.
enum class ErrorCode {
    NotFound,  ///< A file or entry does not exist.
    Truncated, ///< Data ended before its own header said it would.
    Invalid,   ///< Data is present but breaks its format's rules.
    Io,        ///< The operating system reported a read or write failure.
};

/// A recoverable error: a code to branch on and a message for the log.
struct Error {
    ErrorCode code;
    std::string message; ///< For people reading logs; never parsed by code.
};

} // namespace coney

/// Stops the program with the condition, file and line when `condition` is false.
/// Only for programmer errors; never for bad input data.
#define CONEY_ASSERT(condition, message) /* defined in src/core/assert.h */
```

A short example, continuing the `WadIndex` above:

```cpp
std::expected<WadIndex, Error> WadIndex::parse(std::span<const std::byte> dirData) {
    Reader reader(dirData);
    auto entryCount = reader.readU32Le();
    if (!entryCount) {
        return std::unexpected(entryCount.error());
    }
    // The 12 bytes after the count are padding: the entries start at 0x10.
    if (auto seeked = reader.seek(0x10); !seeked) {
        return std::unexpected(seeked.error());
    }
    // Check the size before allocating, so a corrupt count can't make us reserve gigabytes.
    constexpr std::size_t kEntrySize = 12;
    if (reader.remaining() / kEntrySize < *entryCount) {
        return std::unexpected(Error{ErrorCode::Truncated, "WARRIORS.DIR is shorter than its entry count"});
    }

    WadIndex index;
    index.m_entries.reserve(*entryCount);
    for (std::uint32_t i = 0; i < *entryCount; ++i) {
        // The size check above covers every read in this loop, so these cannot fail.
        WadDirEntry entry;
        entry.wadOffset = reader.readU32Le().value();
        entry.size = reader.readU32Le().value();
        entry.nameHash = reader.readU32Le().value();
        index.m_entries.push_back(entry);
    }
    CONEY_ASSERT(index.m_entries.size() == *entryCount, "every entry was read");
    return index;
}
```

Bad data from a disc is never a programmer error: a scratched disc or a modded file must produce an `Error`, not
an assert. A parser that silently accepts truncated data is a Critical review finding.

## Memory and data

- **RAII for every resource.** Memory, files, SDL and librw handles are owned by an object whose destructor
  releases them, so no early return can leak them.
- **No owning raw pointers.** Ownership is `std::unique_ptr`, a container, or a small RAII wrapper. A raw pointer
  or reference means "I'm looking at something someone else owns" and nothing more, as `WadIndex::find` above
  shows.
- **Disc data is read through `coney::io::Reader`**, with explicit little-endian reads (`readU8`, `readU16Le`,
  `readU32Le`, `readF32Le`, `seek`, `remaining`). Each read checks the bounds and returns
  `std::expected<T, Error>`, so running off the end of a buffer is an error rather than a crash.
- **Never `reinterpret_cast` a buffer to a struct or an integer**, even when the struct matches the file layout
  byte for byte. Three things go wrong:
    - *alignment:* a `std::uint32_t` read from an arbitrary offset of a byte buffer may be misaligned, which is
      undefined behaviour and faults on some processors;
    - *endianness:* the PS2 data is little-endian; reading it field by field makes the byte order explicit in the
      code, and the code stays correct on any host;
    - *strict aliasing:* accessing bytes through a pointer to an unrelated type is undefined behaviour, and
      optimising compilers do exploit it. Struct padding can also differ between compilers.

    `Reader` assembles each value from bytes, which avoids all three, and the cost is negligible next to disc I/O.

The `Reader` interface, from `src/fileio/reader.h` (abridged; it also has `readBytes`):

```cpp
namespace coney::io {

/// Reads little-endian values from a byte buffer it does not own, with bounds checks.
class Reader {
public:
    explicit Reader(std::span<const std::byte> data);

    std::expected<std::uint8_t, Error> readU8();
    std::expected<std::uint16_t, Error> readU16Le();
    std::expected<std::uint32_t, Error> readU32Le();
    std::expected<float, Error> readF32Le();

    /// Moves to an absolute offset. Fails with ErrorCode::Truncated past the end.
    std::expected<void, Error> seek(std::size_t offset);

    std::size_t position() const; ///< The offset of the next read.
    std::size_t remaining() const; ///< Bytes left after the current position.
};

} // namespace coney::io
```

## Platform code

**Code that talks to the operating system or a graphics API lives only in `src/platform/`**: windowing, input,
timing, threads, file-system paths, and the SDL3 and librw glue. Everything else in `src/` is portable C++ that
calls `src/platform/` through Coney's own interfaces.

This keeps three platforms working with one engine: a port problem has one place to look, and the rest of the
engine builds and tests the same way everywhere. An `#ifdef _WIN32` outside `src/platform/` is a review finding.

The same boundary protects the engine's **test mode**, a recorded requirement: Coney must be able to run with a
fixed timestep, seeded randomness, scripted input and a local control channel, so that tests and reference
comparisons against the original game are repeatable. Engine code therefore never reads the clock, the random
source or the input devices directly; it asks the platform layer, which test mode can replace. Don't design this
out.

## Tests

Everything that can be tested without the game is written test-first, with Catch2 under `tests/` (mirroring
`src/`). Format code is tested on small synthetic fixtures **we write** byte by byte, never on files taken from the
disc. Tests that need the player's disc find it through `coney.local.toml`, skip when it isn't configured, and
print only aggregates (counts, hashes matched), never content. See
[LEGAL.md](repo:LEGAL.md#no-game-data).

## Python {#python}

`python/coney_tools` holds Coney-specific automation: the WAD extractor and name recovery, the PCSX2 bridge, and
the harness that drives a running Coney or PCSX2 with scripted input. Tooling that would be useful to other
reverse-engineering projects goes to Rekit instead, once a second project needs it.

- **Python 3.12 or newer**, managed with [uv](https://docs.astral.sh/uv/): `uv sync` sets up the environment and
  `uv run` runs inside it, so everyone uses the same locked dependencies.
- **One command-line entry point:** `coney-tools <group> <command>`, for example `coney-tools wad extract`. No
  loose scripts: a script outside the CLI has no tests, no `--help` and nowhere obvious to be found. The planned
  groups are `wad`, `xbox`, `emu` and `harness`.
- **ruff** formats and lints, **mypy --strict** type-checks, and **pytest** tests. All three run in CI; ruff format
  also runs in pre-commit. Strict typing matters here because these tools parse binary formats, where a wrong type
  is a silent wrong answer.
- **`pathlib` only** for paths, never string concatenation or `os.path`. Every tool runs on Windows, Linux and
  macOS, and `pathlib` handles the separators and drive letters.
- **Docstrings** on every public module, class and function: a one-line summary, then whatever a caller needs
  (arguments, return value, errors raised), and a link to the research page when the code implements a format.

The same licence header, `@orig` and *why* rules apply as for C++. An example:

```python
# SPDX-License-Identifier: GPL-3.0-or-later
"""Name hashing for WARRIORS.DIR lookups."""

import zlib


def name_hash(path: str) -> int:
    """Return the hash WARRIORS.DIR stores for `path`.

    The game lowercases a name before hashing it, so the hash ignores letter case.
    Research: docs/research/name-hash.md
    """
    return zlib.crc32(path.lower().encode("ascii"))
```

## File size

A source file passing about **500 lines** is a prompt to split it, usually along the lines of the original's own
classes. Not a hard limit, but a reviewer will ask why. Large files are where a reader loses the thread, and they
make reviews and merges harder.
